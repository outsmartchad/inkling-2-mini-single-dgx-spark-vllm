# How Inkling 2 Mini reads a prompt and writes a reply

## How the model works

Suppose you ask, “Which word completes ‘the cat sat on the …’?” Inkling has to produce the first piece of its reply before it can produce the second. A **tokenizer** breaks the text and the chat template’s role markers into pieces and assigns each piece an integer. A piece can be a whole word, part of one, punctuation or a control marker. The integer picks a row from an **embedding** table. That row is a vector of 2,304 numbers, the starting representation of this piece wherever it appears. As the vector passes through the decoder, those numbers change to reflect the words around it. The checkpoint specifies 200,058 unpadded vocabulary entries and a padded vocabulary size of 201,024. [Pinned model configuration](https://huggingface.co/thinkingmachines/Inkling-2-Mini/blob/ed40e7da625f594fc9c4990f5f66be24873c22d7/config.json) · [Model card](https://thinkingmachines.ai/model-card/inkling-2-mini/)

A **weight** is a number learned during training, such as an element of the embedding table. All conversations use the same weights. A **hidden state** is a vector calculated with those weights for a particular token in a particular conversation. Some intermediate results also have to survive until the next token arrives. Inkling keeps attention data and short-convolution history for each request. Starting a new conversation gives it a different history even though the server uses the same underlying model. [Checkpoint configuration](https://huggingface.co/thinkingmachines/Inkling-2-Mini/blob/ed40e7da625f594fc9c4990f5f66be24873c22d7/config.json) · [vLLM integration](https://vllm.ai/blog/2026-11-20-inkling2-mini)

### Inside a decoder layer

For the final prompt position in the cat example, attention lets the representation incorporate “cat”, “sat” and other preceding pieces. A **query** encodes what information the current position seeks. A **key** describes what an available position can match, and a **value** carries information it can contribute. Comparing the query with eligible keys gives scores. Attention converts these into weights and sums the corresponding values. Causal attention allows the current and earlier positions. During generation the server saves the old keys and values in a **KV cache** so that each new query can use them again. [Attention mechanism](https://arxiv.org/abs/1706.03762) · [Architecture notes](https://vllm.ai/blog/2026-11-20-inkling2-mini)

Inkling uses 24 query heads with 8 key/value heads. A head is a separate learned view of the same sequence. Groups of three query heads share key/value data. Five layers in each group of six use a 1,024-position sliding window. The sixth can look across the full available history. This gives many layers a bounded search and others a direct connection to distant positions. The attention design includes a learned relative-position bias, a sink that can absorb attention weight, and a gate controlling the contribution of the result. Short convolutions also combine nearby positions, with a kernel size of four. A server must remember a short tail for these convolutions as well as the attention cache. [Pinned dimensions and layer IDs](https://huggingface.co/thinkingmachines/Inkling-2-Mini/blob/ed40e7da625f594fc9c4990f5f66be24873c22d7/config.json) · [vLLM architecture description](https://vllm.ai/blog/2026-11-20-inkling2-mini)

The other major calculation in each layer is a **mixture of experts**. Here an expert is a feed-forward network that transforms the vector for one position. A router examines that vector, chooses 8 of the layer’s 128 networks and weights their contributions. The checkpoint specifies zero shared experts. A later token may select a different eight, even in the same layer. All 128 sets of weights must therefore be available for serving. Their sparse use is why 26.4 billion total parameters can give about 3.4 billion active parameters before accounting for repeated layer visits. An expert’s index tells us which computation ran. The model card assigns no topic label such as “grammar” to that index. [Thinking Machines model card](https://thinkingmachines.ai/model-card/inkling-2-mini/) · [Router configuration](https://huggingface.co/thinkingmachines/Inkling-2-Mini/blob/ed40e7da625f594fc9c4990f5f66be24873c22d7/config.json)

The decoder carries a residual representation forward and adds learned updates along the way. RMS normalization scales a vector by its typical magnitude to give a sublayer a controlled input. Inkling also groups six layers into a block and learns how much to read from block representations accumulated so far. These **attention residuals** mix information across depth. Ordinary token attention, described above, mixes information across positions in the sentence. The distinction matters in the middle of this model, where a later pass through a layer can read information computed by an earlier pass for the very same token. [Loop integration and residual reads](https://vllm.ai/blog/2026-11-20-inkling2-mini) · [NeMo model reference](https://docs.nvidia.com/nemo/automodel/nightly/model-coverage/vision-language-models/thinkingmachines/Inkling-2-Mini)

### Why 24 stored layers give 48 visits

| Stage | Stored layer IDs, zero-based | What happens to the token |
| --- | --- | --- |
| Prelude | 0–5 | Derives a starting representation from the input. |
| First core pass | 6–17 | Runs two six-layer blocks from the prelude output. |
| Second core pass | 6–17 | Restarts from that prelude output and reads messages from pass one. |
| Third core pass | 6–17 | Restarts from the same prelude output and reads messages from pass two. |
| Coda | 18–23 | Continues from the third pass and prepares the prediction. |

On pass one there is no previous-pass message. On each later pass, a learned query reads the previous pass’s two block representations. Each core layer has four such reads, one apiece for its query, key, value and expert input. A rank-64 controller combines the current input and its message, adjusting how much of each to retain in each channel. The reader for the attention key can therefore ask for different information than the reader for the expert. The model makes 48 message reads in each later pass. The number 64 is an internal controller dimension, independent of the number of generated tokens. [Loop configuration](https://huggingface.co/thinkingmachines/Inkling-2-Mini/blob/ed40e7da625f594fc9c4990f5f66be24873c22d7/config.json) · [Controller equations and cache implementation](https://vllm.ai/blog/2026-11-20-inkling2-mini)

The same weights perform the three core passes, giving six plus three times twelve plus six layer visits. The model author puts the repeated computation at about 5.4 billion effective active parameters per token. Reusing weights saves storage. Earlier tokens still had different representations on passes one, two and three. To use the right history, each visit has its own KV and convolution state. For example, when the token following “sat” reaches the second pass of layer 6, it can read the second-pass layer-6 history of “sat”. vLLM represents the resulting 48 cache instances as separate logical layers. [Parameter accounting](https://thinkingmachines.ai/model-card/inkling-2-mini/) · [Pass-specific state in vLLM](https://vllm.ai/blog/2026-11-20-inkling2-mini)

After the coda, the language-model head produces a **logit**, or unnormalized score, for each possible next piece. Inkling configures a soft cap of 30 for the final logits. The sampler turns scores into a choice, using settings such as temperature to control how strongly it favors high-scoring tokens. If it chooses the token for “mat”, that choice becomes part of the input for the next prediction. The tokenizer turns the accumulating IDs back into text. Reasoning mode can generate reasoning tokens before answer tokens. Each costs decode work. For an image, a separate 23-layer vision transformer encodes patches and an adapter merges neighboring features into the same 2,304-wide space used by text. The decoder can condition its text output on both. [Text and vision configuration](https://huggingface.co/thinkingmachines/Inkling-2-Mini/blob/ed40e7da625f594fc9c4990f5f66be24873c22d7/config.json) · [Input and output modalities](https://thinkingmachines.ai/model-card/inkling-2-mini/)

## How this recipe runs it on one DGX Spark

### Loading the model and admitting a request

`./bin/recipe.sh fetch` obtains the pinned ARM64 vLLM image and checkpoint revision `ed40e7da`. The 18.8 GiB checkpoint includes the native draft module. The routed experts in stored layers 0–19 use NVFP4 and those in layers 20–23 use MXFP8. These are compressed floating-point weight representations with scales. Compact weights reduce the bytes the GPU has to read when it uses an expert. Other tensors have their own representations, and the default KV dtype is automatic. A four-bit expert weight says nothing by itself about how many bytes a cached key occupies. [Fetch and launch script](../bin/recipe.sh) · [Weight formats by layer](https://vllm.ai/blog/2026-11-20-inkling2-mini) · [Checkpoint pin](../results/baseline/checkpoint.json)

`serve` mounts the model snapshot read-only and a separate writable vLLM/Triton cache for compiled kernels. It prefetches safetensors during loading and serves an OpenAI-compatible endpoint on the Spark’s loopback address, port 18905. A chat request supplies messages, a model ID and sampling options. The template produces the input sequence. The scheduler places that request alongside others with available memory. The Inkling reasoning and tool parsers interpret generated markers for the client. The launcher admits one image and zero videos per prompt. The published timing runs sent text. [Recorded arguments](../results/baseline/launch.args.txt) · [Client example and readiness check](../README.md)

**Prefill** processes known prompt tokens and populates the pass-specific caches. For a long prompt the scheduler can divide that work across iterations, with a maximum batch budget of 8,192 tokens. Prefix caching is disabled in this run, so sending the same prompt again still incurs prefill. **Decode** starts when the model can predict an output from that prefix. The scheduler can work on up to five sequences, each with an input-plus-output ceiling of 262,144 tokens. The model’s published ceiling is 1,048,576. This launch selects a smaller limit. A CUDA graph lets vLLM replay recorded GPU operations with less CPU launch overhead. The recipe uses breakable graphs, and vLLM also fuses the four message reads and batches their controller projections. [Launch limits](../results/baseline/launch.args.txt) · [Runtime implementation](https://vllm.ai/blog/2026-11-20-inkling2-mini) · [Graph comparison](optimization.md)

### What native DSpark does

The drafter reads four target representations, at configured visit IDs 5, 23, 41 and 48. These sample the prelude, the second and third passes, and the final output. Its three-layer network combines information from those depths and proposes multiple positions together. Its lightweight recurrent correction head lets the choice at one draft position influence the next. The checkpoint specifies rank 256 for that head and a block size of eight. vLLM requests seven speculative tokens with probabilistic draft sampling. One committed anchor plus seven proposed continuations explains why the two numbers differ. The draft network is already in the snapshot. [Native draft configuration](https://huggingface.co/thinkingmachines/Inkling-2-Mini/blob/ed40e7da625f594fc9c4990f5f66be24873c22d7/config.json) · [Hidden-state inputs](https://vllm.ai/blog/2026-11-20-inkling2-mini) · [DSpark method](https://arxiv.org/abs/2607.05147)

The target evaluates the proposed continuation with causal attention. A verified prefix can advance the output by several positions in a single target call. Once verification rejects a position, later guesses depending on it are unusable. The target’s sampling procedure determines how generation continues. In the “cat sat” example a draft might propose pieces for “mat”, a period and a new sentence. Acceptance through the period allows both pieces onto the stream even if the next guess fails. Drafting incurs its own work, and a seven-token budget gives no guarantee of seven accepted tokens. The recorded classic-graphs screen counted 6,263 acceptances among 31,612 drafted positions, about 19.8% for that instrumentation window. [Classic-graphs counters](../results/tuning/classic-graphs.spec.metrics.txt) · [Matched tuning conditions](optimization.md)

### Reading the measurements

The 0.70 memory-utilization setting governs vLLM’s allocation budget on a GB10 with 128 GB of unified memory. The baseline reported 599,083 shared KV token positions and a sampled GPU-process peak of 81.7 GiB. One request at the launch ceiling can fit within that pool. Five requests all at the ceiling would need 1,310,720 positions. Short requests can share the machine at much higher concurrency than requests close to the limit. Memory samples include model and runtime allocations, and a pool capacity is a count of token positions rather than a measure of model file size. [Baseline and allocation details](baseline.md) · [Memory trace](../results/baseline/inkling.memory.csv)

With high reasoning effort and a 400-token output budget, the fastest measured one-stream wave decoded 42.7 tokens per second. The fastest five-stream wave delivered 107.8 combined and a median 22.4 per request. Time to first token (TTFT) was 219 ms and 1.73 s respectively. TTFT counts the first reasoning or answer content. In three fresh retrieval prompts per input length, median prefill was 3,149 input tokens/s near 32K and 2,464 near 128K. Median TTFT rose from 10.40 to 53.19 seconds. Two of three 32K requests returned the key within budget, as did all three 128K requests. The remaining 32K response exhausted its output allowance. [Measured summary](../results/baseline/summary.json) · [Retrieval samples](../results/baseline/inkling.prefill.json)

Separate tuning runs used medians of six 256-token waves at each concurrency. Disabling DSpark reduced the single-stream median from about 40 to 37.84 tokens/s. Changing graph mode had little effect on that metric. In a second screen, explicitly selecting FP8 E4M3 for KV increased reported capacity to 836,176 token positions, 40–41% above the bracketing automatic-dtype controls. Five-user throughput dipped, and the single 128K probe per profile took about two to three seconds longer with FP8. All three probes retrieved their key. Those results explain why the published launcher retains automatic KV while a memory-constrained workload might value the extra capacity.
